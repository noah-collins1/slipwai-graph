MINOR

**A generated TypeScript service now has a real mutation run: `make mutation` mutates only the production files a slice branch changed, and `make mutation-full` is the sweep of the service's whole `mutate` list.** Stryker 10.0.0 and its Vitest runner (`@stryker-mutator/core`, `@stryker-mutator/vitest-runner`, both exact) are `devDependencies` of every TypeScript service, installed only from the committed lock and started as `npm exec --no`, so nothing is fetched; each service carries a checked-in `apps/<service>/stryker.config.json` (the files it mutates, `src/**/*.ts` without `main.ts`, `openapi.ts` and, where Postgres is the store, the Postgres adapter), and the project carries one wrapper, `scripts/stryker-mutation.py`, which decides the verdict itself. It reads `apps/<service>/reports/mutation/mutation.json` and fails on a survivor, a timeout or any status but killed and ignored, whatever Stryker's exit status says; a mutant no test reaches is counted and reported, never failed, and a run that leaves no readable report fails. On a `slice/<id>` branch (or with `make mutation SINCE=<ref>` on any checkout) `make mutation` hands Stryker only the changed files its `mutate` list takes, names a file the list excludes as outside Stryker's configured targets, names a changed file under a browser app as not mutated, starts Stryker for the changed service only, and refuses in one line a changed path Stryker's `--mutate` would misread as pattern syntax (a comma, `*`, `?`, `{`, `[`, `!`, a backslash, `+(`, `@(`, or a trailing `:<line>` or `:<start>-<end>` line range); a change to a service's `stryker.config.json`, to `scripts/stryker-mutation.py`, or to a pinned `@stryker-mutator/*` version sweeps it instead, as does a `mutate` list the script cannot read. The reports and sandboxes a run leaves (`.stryker-tmp/`, `apps/*/reports/mutation/`) are ignored by git and left out of the verify stamp's key, `make verify`, `make verify-checks`, `make ci` and the CI workflow are byte for byte what they were, and the twelve committed TypeScript dependency locks move with the manifest. Only a `// Stryker disable next-line <mutator>: <reason>` comment excuses a mutant: `excludedMutations` in the config and block or file-wide disable comments do not, and the wrapper fails a mutant they ignore. The default TypeScript starter's `make mutation-full` fails the day it is generated, because its own starter tests leave survivors; a slice that edits one of those files meets that file's survivors in its scoped `make mutation`. The minimal starter is green, and a fix is planned: a follow-on slice makes the starter's tests kill them. Python and `java-quarkus` still have no tool wired and refuse a changed service with their setup messages.

**Catch-up.** A project made before gains, after `slipwai migrate`, the two devDependencies `@stryker-mutator/core` and `@stryker-mutator/vitest-runner` (each `10.0.0`, exact) in every TypeScript service's `package.json`, `stryker.config.json` per TypeScript service, `scripts/stryker-mutation.py`, the ignore lines, the regenerated `scripts/verify_scoped/rules.json` and the Makefile note; a Go-only project gains no Stryker file. Settle a `package-lock.json` conflict by taking the factory's side (`git checkout --theirs -- package-lock.json`), then run `npm install` so it agrees with your manifests. A project that added a service with `slipwai add-service` is told that `Makefile`, `package-lock.json`, `scripts/verify_scoped/rules.json` and the `package.json` of each service it added (`apps/<service>/package.json`) conflict, because both sides changed the same lines; the Stryker files are already merged. Take the factory's side of all four (`git checkout --theirs -- <file>`, then `git add <file>`), which gives that `package.json` the two devDependencies at `10.0.0`; add back any dependency of your own beside them and run `npm install`, after which `npm ci` accepts the lock. `Makefile` and `scripts/verify_scoped/rules.json` are a pair: `rules.json` records the text of the `Makefile` the factory wrote, and no command rewrites it, so a Makefile edit you re-add makes the scoped gate run the full gate, as it does for any edited Makefile; keep your own targets in a file `make verify` does not read (`make -f deploy.mk …`) to scope again. Where Stryker was wired by hand, remove your hand-wired script and config and keep the factory's `stryker.config.json` and `scripts/stryker-mutation.py`, or keep your own and accept that `make mutation` sweeps the service whenever the factory's wrapper or the pinned versions change; migrate lists a `stryker.config.json` you wrote as a conflict and never overwrites it. `make mutation-full` now runs Stryker for a TypeScript service, and on the default starter it will report the starter's own survivors (about ninety, in `app.ts`, `events.ts`, `tracing.ts`, the projections, `config.ts` and the memory stores) and a timeout: those are your tests' weak spots, not noise, and the minimal `standard` starter with no transport and the memory store is green. Python and `java-quarkus` stay recorded stubs that refuse with their setup message until a tool is wired. No `project.json` key changes.
