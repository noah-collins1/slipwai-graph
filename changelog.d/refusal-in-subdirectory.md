**`adopt --refresh`, `--confirm` and `--decline` (experimental: brownfield adoption) now refuse to write over an uncommitted change where the project sits in a subdirectory of its git repository.** Git names a path from the repository's top (`sub/delivery/docs/convergence.md`) and a run names what it writes from the project (`delivery/docs/convergence.md`), so in a subdirectory project no path ever matched. The refusal never fired: a hand edit, a deletion or an untracked file at a path the run writes was written over at exit 0, and `.delivery-tools/written.json`, which is how a run tells its own leftovers from a person's work, stayed empty.

The refusal now looks at the changes under the project's own directory and names each file as the project spells it, as it does where the project is the top of its repository. What a run leaves uncommitted is recorded the same way, so the next run knows it for its own and writes over it, while a person's edit on top of it is refused. A change elsewhere in the repository neither refuses a run nor is recorded, since nothing here writes there; that includes an edit to a file at the top whose path happens to spell one the run writes, which the earlier code refused by mistake. A project at the top of its repository, or in no repository, sees no change.

**Catch-up.** A repository already adopted in a subdirectory may meet one refusal, once. If an earlier run left regenerated files uncommitted, nothing was recorded for them, and the first refresh, confirm or decline after this change refuses, naming them, because slipwai cannot tell them from an edit of yours. Commit them, or stash them, and run it again; nothing else is asked.
