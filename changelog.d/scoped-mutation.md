**A generated project's `make mutation` is priced per change on a slice branch, and `make mutation-full` is the run it was.** On a `slice/<id>` branch `make mutation` now mutates only the production files that differ from the trunk commit the branch was cut from, staged, unstaged and untracked ones included and nothing committed or stashed, together with the files of any local trunk commits `origin/<trunk>` does not carry yet (where there is a remote but what those commits changed cannot be worked out — no `origin/<trunk>`, or no history in common with it — it runs the sweep instead); `make mutation SINCE=<ref>` mutates the files that differ from that ref on any checkout, CI included, and does not count unpushed trunk commits. Go runs Gremlins over the changed files of the changed services only, and Spring narrows PIT to the changed classes (`Foo` and `Foo$*`) within the pom's `targetClasses` and `excludedClasses`, with the pom untouched; a change to a service's `.gremlins.yaml`, its `pitest-maven` block, `scripts/go-mutation.py`, `scripts/mutation-scope.py` or the `mutation` or `mutation-full` rule sweeps the service or the run instead, as does a `mutation-full` recipe that is not the one the factory wrote, which runs as written, `SINCE` included, and each line the run prints names what it did and why. TypeScript, Python and `java-quarkus` have no mutation tool wired, so for them `make mutation` refuses a changed service with the setup message and names the files it would mutate, as the sweep always has refused; the scope applies once a tool is wired. A Python service stays refused until a later slipwai release wires mutmut, whether or not mutmut is installed, and `make mutation-full` runs mutmut today where it is installed. `make verify`, `make verify-checks`, `make ci` and the CI workflow are byte for byte what they were, and neither mutation target is reachable from them.
