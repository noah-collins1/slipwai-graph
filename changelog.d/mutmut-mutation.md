**A generated Python service now has a real mutation run: `make mutation` mutates only the production files a slice branch changed, and `make mutation-full` is the sweep of the service's whole `src/`.** mutmut 3.8.0 (`mutmut==3.8.0`, exact) is in every Python service's `dev` group, installed only from the committed lock (`uv sync --locked`, so the four committed `uv*.lock` files move with the manifest), each service's `pyproject.toml` carries a `[tool.mutmut]` table (`source_paths = ["src"]`, the default suite without `tests/integration`, and `-p no:xdist`), and the project carries one wrapper, `scripts/mutmut-mutation.py`, which decides the verdict itself. It has mutmut generate the mutants, reads which ones each file holds from the `mutants/<file>.meta` files that step writes and hands `mutmut run` exactly those names, then reads the results from the same files and never from mutmut's exit status, which is 0 when mutants survive: a killed mutant passes, a mutant no test reaches is counted and reported, never failed, and a survivor, a timeout, a mutant never checked or any other status fails the run. On a `slice/<id>` branch (or with `make mutation SINCE=<ref>` on any checkout) `make mutation` hands mutmut only the changed files its `[tool.mutmut]` table takes, names a file the table leaves out as outside mutmut's configured targets, starts mutmut for the changed service only, and refuses in one line a changed path holding `*`, `?` or `[`, which `mutmut run` would read as a pattern over mutant names; a file in which mutmut finds nothing to mutate is reported as no mutant to run, not as a failure. A change to a service's `[tool.mutmut]` table or mutmut requirement, to its lock's `mutmut` or `libcst` entries, or to `scripts/mutmut-mutation.py` sweeps it instead, as does a table the script cannot read. Every run is a fresh one: the wrapper removes `mutants/` first, so mutmut's cache never lets a gutted test pass on an earlier run's kills, and one run holds a service at a time. It refuses with exit 2, before starting anything, a host without `os.fork` (Windows runs it under WSL), a project without `uv`, a lock that disagrees with the manifest and an environment whose mutmut is not 3.8.0; it drops a `PYTEST_ADDOPTS` from the environment it hands mutmut, and says so, because it would change how every mutant's tests run. Only a bare `# pragma: no mutate` comment excuses a mutant: `# pragma: no mutate block`, `start` and `end`, and `do_not_mutate_patterns` in the table silence mutants nobody looked at, and the wrapper fails the run that holds them. `apps/*/mutants/` is ignored by git and left out of the verify stamp's key and `check-imports`; `make verify`, `make verify-checks`, `make ci` and the CI workflow are byte for byte what they were. The default Python starter's `make mutation-full` reports survivors the day it is generated, because its own starter tests leave them; a slice that edits one of those files meets that file's survivors in its scoped `make mutation`. The minimal starter, with no HTTP framework and the memory store, is green. `java-quarkus` still has no tool wired and refuses a changed service with its setup message.

**Catch-up.** A project made before gains, after `slipwai migrate`, `mutmut==3.8.0` in every Python service's `dev` group and the `[tool.mutmut]` table in its `pyproject.toml` where the files merge, `scripts/mutmut-mutation.py`, the `apps/*/mutants/` ignore line, the regenerated `scripts/verify_scoped/rules.json` and the Makefile note; a Go-only or TypeScript-only project gains none of them. The lock is yours to redo wherever your `pyproject.toml` differs from the factory's (a dependency of your own): `migrate` brings the factory's `uv.lock`, which agrees with the factory's manifest and not with yours, so until `uv lock --project apps/<service>` has been run for that Python service, `make mutation` exits 2 with a line saying `uv.lock` does not agree with `pyproject.toml` (the wrapper's `uv sync --locked` is refused), and `make mutation-full` exits 2 the same way. A service added with `slipwai add-service` is listed as a conflict in `apps/<service>/pyproject.toml` and `apps/<service>/uv.lock`, because both sides changed the same lines: take the factory's side of each (`git checkout --theirs -- <file>`, then `git add <file>`), add back any dependency of your own, and run `uv lock --project apps/<service>` so that `uv sync --locked` accepts it. `make mutation-full` now runs mutmut for a Python service, and on the default starter it will report the starter's own survivors: those are your tests' weak spots, not noise, and the minimal `standard` starter with no transport and the memory store is green. A leftover `mutants/` directory or `.mutmut-cache` file from an earlier hand-wired run may be deleted; the wrapper starts from a fresh `mutants/` whatever it finds. Windows needs WSL, since mutmut needs `os.fork`. Where mutmut was wired by hand, remove your own pin, table and script and keep the factory's, or keep your own and accept that `make mutation` sweeps the service whenever the factory's wrapper, your table or the pinned versions change, and that the wrapper refuses any mutmut but 3.8.0. Pragma forms other than the bare `# pragma: no mutate`, and `do_not_mutate_patterns` in `[tool.mutmut]`, fail the run. `java-quarkus` stays a recorded stub that refuses with its setup message until a tool is wired. No `project.json` key changes.
