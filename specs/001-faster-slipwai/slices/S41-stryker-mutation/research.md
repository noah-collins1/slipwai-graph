# Research: S41-stryker-mutation

Every statement about Stryker's behaviour below cites the run or the source it was read from. Runs were made on
2026-10-08 in scratch starters generated by this branch's factory (`PYTHONPATH=src python3 -B -m slipwai generate …
--no-init --no-install --skip-checks`) under `/tmp/cruise29/s41-scratch/`: **demo** is the default answer on every
axis (`event-modelling`, `react-vite`, Fastify, Postgres), **mini** is `--profile standard --frontend none --http none
--event-store memory`. Machine: 12th Gen Intel i5-12400, `nproc` 12, Linux 7.0.0-31, Node v22.22.1, npm 9.2.0 (the
starter's `.nvmrc` says 24; Stryker 10 needs Node ≥ 22, `npm view @stryker-mutator/core@10.0.0 engines`).

## R1 — Does Stryker run against the starter's Vitest 4.1.11 and TypeScript 7.0.2? (G3, D215 "would reverse if")

**Decision:** yes, with the Vitest runner, pinned exactly at `@stryker-mutator/core` **10.0.0** and
`@stryker-mutator/vitest-runner` **10.0.0** (the current release of both: `npm view … version` → 10.0.0, published
2026-08-14), and with one setting that keeps Stryker away from TypeScript's JavaScript API.

**Evidence.**
- Peer ranges: `npm view @stryker-mutator/vitest-runner@10.0.0 peerDependencies` → `{ vitest: '>=2.0.0',
  '@stryker-mutator/core': '10.0.0' }`. Vitest 4.1.11 is inside it. `npm --workspace apps/service install -D
  --save-exact @stryker-mutator/core@10.0.0 @stryker-mutator/vitest-runner@10.0.0` added 162 packages with no peer
  warning.
- **The first run failed:** `TypeError: ts.parseConfigFileTextToJson is not a function` at
  `@stryker-mutator/core/dist/src/sandbox/ts-config-preprocessor.js:46`. TypeScript 7 is the native compiler and ships
  no JavaScript compiler API — the same break `biome.jsonc` records for typescript-eslint. The preprocessor only
  rewrites `extends`/`references` paths that would leave the sandbox (its own doc comment, lines 3–19), and it runs
  only when the file named by the `tsconfigFile` option is among the project's files (`project.files.get(...)`, line
  42). The starter's `tsconfig.json` has neither `extends` nor `references` (`typescript_config()` in
  `src/slipwai/project/languages/typescript.py`).
- **With `"tsconfigFile"` naming a file that does not exist the run completes**: demo, 10 of 37 files, 519 mutants,
  exit 0, 41.1 s wall, 321 MB peak RSS (`/usr/bin/time -v`). The schema says the option exists for that rewrite and for
  the type-checker plugin, nothing else (`schema/stryker-schema.json`, `tsconfigFile`); a grep of every
  `@stryker-mutator/*` dist file finds it read in `ts-config-preprocessor.js` only.
- **Alternatives considered.** `inPlace: true` also skips the preprocessor (line 31) but mutates the working tree,
  so a killed run leaves mutated sources in the developer's checkout — refused. The command runner has no per-test
  coverage and would run the whole suite per mutant (G3) — not needed. Pinning TypeScript 5 for Stryker alone would
  put a second compiler in every project — refused.

**What this costs a project later:** if a project adds `extends` or `references` that leave the service directory,
the sandbox copy will not resolve them and the initial test run fails red — a loud failure, never a silent pass.
The config's `tsconfigFile_comment` says so. ADR 0009 records it.

## R2 — The type-checker plugin (D215 (c))

**Decision:** no checker. `@stryker-mutator/typescript-checker@10.0.0` installed beside the two and run with
`--checkers typescript` fails at start: `An error occurred during initialization of the "typescript" checker. Inner
error: TypeError: Cannot read properties of undefined (reading 'fileExists')` at `typescript-checker.js:62` — it is
built on the same JavaScript API TypeScript 7 removed. Without a checker a type-invalid mutant runs under Vitest's
type-stripping and is judged by the tests like any other; nothing reports `CompileError` in this configuration.

## R3 — `--mutate` replaces the config's list (G2, D213 item 3)

**Decision:** the scope is intersected with the config's `mutate` list in Python, before Stryker starts; Stryker is
then handed only files the list already matches.

**Evidence.** `stryker run --mutate src/main.ts` against a config whose list excludes `src/main.ts` mutated it (22
mutants). Source: `ProjectReader.resolveFileDescriptions` (`core/dist/src/fs/project-reader.js:89–140`) walks
`this.mutatePatterns` — the CLI value replaces the option — and only the mutation-testing server passes
`targetMutatePatterns`, the intersection (`stryker-server.js:156, 207`; `stryker.js:29` passes `undefined`).

**How the list is read** (`project-reader.js:96–114`, `FileMatcher` in `@stryker-mutator/util`): patterns apply in
order, a positive one marks what it matches, a `!` one unmarks; each is `path.resolve`d against the working directory
(the service) and matched with minimatch 10.2.6 with `dot: false`. A pattern ending `:<line>-<line>` is a range
(`MUTATION_RANGE_REGEX`, line 26). The reader in the wrapper implements exactly the subset the factory writes —
literal segments, `*` within a segment, `**` as a whole segment, a leading `!`, a leading `./` — and calls anything
else (`?`, `[`, `{`, `(`, `+`, `@`, `\`, a `**` inside a segment, `..`, an absolute path, a range, a non-string, a
missing or non-list `mutate`) *unreadable*, which is the service's sweep (D213 item 3). Dot rule: `*` and `**` never
match a segment starting with `.`, as minimatch's `dot: false`.

## R4 — The verdict and the report (D212)

- **Statuses** in `mutation.json` (schema 1.0, `mutation-testing-report-schema`): `Killed`, `Survived`, `NoCoverage`,
  `Timeout`, `CompileError`, `RuntimeError`, `Ignored`, `Pending`. The demo report holds `Killed` 415, `Survived` 90,
  `NoCoverage` 13, `Timeout` 1. Each mutant carries `mutatorName`, `replacement`, `location.start.line/column`,
  `status`. The wrapper passes `Killed` and `Ignored`, counts `NoCoverage`, and fails on everything else, unknown
  strings included.
- **Stryker passes what D212 fails:** with `thresholds.break: null` the demo run with 90 survivors and a timeout
  exited 0 — the wrapper's reading of the report is the only judge.
- **Zero mutants.** With Vitest's `related` mode on (the default), a scoped run of a types-only file instruments 0
  mutants, finds no related test, logs `No tests were executed. Stryker will exit prematurely` and exits **1 with no
  report**; so does an untested entry file. With `"vitest": {"related": false}` the same run executes the whole suite
  once, exits 0 and writes a report whose `files` is `{}` (types-only file, 3.9 s) — the evidence D212 item 4 needs.
  The cost is the initial test run takes the whole suite instead of the related subset; per-mutant selection is still
  per-test coverage (`perTest`, the dry run's log line). **Decision:** `related: false`.
- **Report path:** the JSON reporter writes `reports/mutation/mutation.json` under the service
  (`JsonReporter` log line); the HTML reporter writes `reports/mutation/mutation.html` beside it. The wrapper deletes
  both before a run (D212 item 7), and `incremental` is `false` in the config and never passed.
- **Clean slate and the sandbox:** `cleanTempDir` defaults to `true`, which deletes only after a successful run
  (schema); even with `"always"` an empty `.stryker-tmp/sandbox-*` directory is left behind (observed). The wrapper
  removes `<service>/.stryker-tmp` before and after the run, and the gitignore and the stamp's exemptions name both
  paths.

## R5 — What a sandbox left behind holds (G6, AC-S41-9)

`symlinkNodeModulesIfNeeded` (`sandbox/sandbox.js:74–100`) links each `node_modules` found by
`findNodeModulesList(process.cwd())` (`utils/file-utils.js:80–100`), a breadth-first walk **below** the working
directory only. In the workspace layout the service has no `node_modules` of its own: a kept sandbox
(`--cleanTempDir false`) holds a real `node_modules/` with Vite's caches and no link at all. Where a service does have
one, the link points back inside the service. So no sandbox link leads outside the deployable, and `verify-scoped`'s
reach scan (`verify_scoped/reach.py`, `link_reach`) reads none as a reach. **Decision:** no change to `reach.py`; a
test pins both shapes.

## R6 — Installing, never fetching (G1, G5, D215 (a))

- `make`'s one install target is `node_modules/.package-lock.json: package.json package-lock.json` (`npm ci`, then a
  touch) in `shared_packages.py`; a prerequisite on `mutation-full` makes `mutation-scope.py` read the recipe as the
  project's own (`prerequisites(written)` at its line 920) and sweep every run (G1). **Decision:** the wrapper
  installs, by the same rule as that target: when the marker is missing or older than either manifest at the project
  root it runs `npm ci` there and touches the marker. The family verify script already does the same
  (`if [ ! -d node_modules ]; then npm ci; fi`, `repository_files`). `npm ci` installs exactly the lock.
- Stryker is started as `npm exec --no -- stryker run …` from the service directory: `--no` makes npm refuse rather
  than download a package it does not have (npm-exec docs, "--no"; observed from `apps/service` with `npx --no`). Before
  that the wrapper looks for `node_modules/@stryker-mutator/core/package.json` and
  `node_modules/@stryker-mutator/vitest-runner/package.json` from the service up to the project root; missing either is
  exit 2 with one setup line. No `npm` on `PATH` is exit 2 with one line.
- Timing: `npm ci` with the two added (438 packages, warm cache) 3.1 s against 2.5 s for 276 without them. `npm audit
  --audit-level=critical` on the demo's new tree exits 0 (G17).

## R7 — Which versions a change to sweeps (D215 (b))

The service's `package.json` names the two in `devDependencies` (exact); the workspace lock at the project root names
each resolved package under a `packages` key ending in `node_modules/@stryker-mutator/<name>` (npm lockfile v3, read
from the demo's lock). **Decision:** the wrapper exposes `versions(text, lock)` → `{name: version}` for every
`@stryker-mutator/*` entry; the scope script compares base and working tree for the service's manifest and for the
root lock, and a side that does not parse counts as changed (D138 item 3). A changed lock sweeps every TypeScript
service, since they share it.

Under D212 the **default** TypeScript starter's `make mutation-full` will fail on day one: 90 survivors and 1 timeout

## R10 — What 10.0.0 lets the wrapper tell about an `Ignored` mutant (D219, T028)

Run in scratch: `npm i @stryker-mutator/core@10.0.0` under `/tmp/cruise29/s41-impl-a/`, then `stryker run` with the
`command` test runner (`command: "true"`, `coverageAnalysis: off`, the `json` reporter) over one file holding, in order, a
`// Stryker disable next-line StringLiteral: equivalent, it is only a label` comment, a next-line one with no reason, a
block `// Stryker disable StringLiteral: block scope reason`, then `// Stryker restore StringLiteral`, and a boolean under
`mutator.excludedMutations: ["BooleanLiteral"]`. The report (`mutation.json`) gave: the next-line mutant `Ignored` with
`statusReason` "equivalent, it is only a label"; the reason-less next-line one `Ignored`, "Ignored using a comment"; the
block one `Ignored`, "block scope reason"; the excluded one `Ignored`, `Ignored because of excluded mutation
"BooleanLiteral"`; a mutant after `restore` `Survived`, no reason. Read in
`instrumenter/dist/src/transformers/directive-bookkeeper.js` and `babel-transformer.js:188-190`: the reason is the
directive's own text (default "Ignored using a comment") for all three comment scopes, and the `excludedMutations`
reason is checked after the directive's, so a mutant that has a comment never reads as excluded. **So** the report tells
`excludedMutations` apart by `statusReason` (the "Ignored because of excluded mutation" prefix) but cannot tell a
next-line comment from a block or file-wide one that gives a reason. **Decision:** the wrapper fails the excluded prefix,
and for every other `Ignored` mutant reads the source line above `location.start.line` (the report's `files[name].source`
where it has one, else the file in the service): it must be `// Stryker disable next-line <mutators>: <reason>` with the
mutant's `mutatorName` among the comma-separated names (case-insensitive; `all` does not count) and a non-empty reason.
A `/* ... */` form of the directive, which Stryker also reads, and a comment separated from its statement by a blank line
fail closed. A source that cannot be read fails. The wrapper counts such mutants as "ignored without a next-line comment".

## R11 — How Stryker 10.0.0's Vitest runner turns a failing `beforeAll` into `Survived`, and what the report keeps (D217, T032)

Run in scratch: the default TypeScript starter generated by this worktree's `./slipwai`, `npm ci`, then `make mutation-full`
(49 s, 519 mutants), and `@stryker-mutator/vitest-runner` 10.0.0's `dist/src/vitest-test-runner.js` and `vitest-helpers.js`
read. `run()` collects `ctx.state.getFiles()` tests and sets `failure` only when a test's own `result.state` is `fail`. For
a test that Vitest *skipped* because a hook threw, `convertTestToTestResult` looks up `findSuiteError(test.suite)`, which
turns the skip into a failure only where an enclosing *suite* has `result.state === 'fail'`; a hook at the top of the file
(the starter's `tracing.test.ts` `beforeAll`) has no enclosing suite (`test.suite` is undefined), so the five tests stay
`Skipped` and the file's own failed state is never read. `errorsSet` (unhandled errors, `DryRunStatus.Error`) is consulted
only when `!failure` and holds unhandled errors, not a hook's. **So** the run is `Complete`, no test failed, and the
mutant is `Survived`; the only trace is `testsCompleted`, which core computes from the tests that are not `Skipped`
(`api/dist/src/test-runner/run-result-helpers.js:17`): 81 for the five against 86 for every other static mutant. No setting
turns this into a kill: `bail`, `disableBail`, `vitest.related` and `coverageAnalysis` do not touch what `run()` reads, and
the only other route, a reporter in the project's own Vitest config that rewrites task state, would live in the user's test
configuration. **Decision:** read the report. The json report's `testFiles` lists the dry run's tests (86 here), and a
static mutant (`static: true`, run under every test) with `Survived` and `testsCompleted` below that count is failed as
`Incomplete`, with its own line and count, never as `Survived` and never as `Killed`, because the report cannot say whether
a hook threw or an `it.skipIf` the mutant flipped skipped the tests. A mutant that is not static runs only its covering
tests and is never compared; a report with no `testFiles` leaves the tool's `Survived` as it is (a failure either way). A
starter with an `it.skip` of its own would label every static survivor `Incomplete`, which is still a failure.
**Real run, default starter:** before, 415 killed, 13 not covered, 90 survived, 1 timed out; after, 415 killed, 13 not
covered, 85 survived, 5 survived with the suite incomplete (`tracing.ts` 81:5 ×2, 81:44, 91:7 `false` and `!==`), 1 timed
out. The real survivor on `tracing.ts` 91:7 is `ConditionalExpression → true`.

## R12 — Which constructs Stryker 10.0.0 mutates, for what `holds_code` counts (AC-S41-3, T026, T033)

Source: `@stryker-mutator/instrumenter` 10.0.0, `dist/src/mutators/`: arithmetic-operator, array-declaration,
arrow-function, assignment-operator, block-statement, boolean-literal, conditional-expression, empty-expression,
equality-operator, logical-operator, method-expression, object-literal, optional-chaining, regex, string-literal,
unary-operator, update-operator. There is no numeric-literal mutator. Probed in scratch with the instrumenter's
`instrument()` over one-line files (`mutate: true`): `export const A = 0;` (also typed, `10n`, `0xff`, `1.5e3`, `let`,
`null`, `undefined`, `B`, `B.c`, `0 as const`, `0 satisfies number`) gave 0 mutants; `-1` gave a `UnaryOperator`, `'x'` and
`` `x` `` a `StringLiteral`, `true` and `!B` a `BooleanLiteral`, `[]` an `ArrayDeclaration`, `{...B}` an `ObjectLiteral`.
**Decision (T033):** besides type declarations, imports and re-exports, a top-level statement is not code for `holds_code`
only when it is `[export] const|let|var NAME[: plain type] = <numeric literal | null | undefined | name or member path>
[as const]`; every other statement, including anything the scanner cannot classify (`(0)`, a second declarator, a call),
is code and fails closed. The starter's `read-models.ts` (`export const FROM_THE_BEGINNING = 0;` and types) is now *no
mutant to run*, as `demo/q4d-starter-port-with-const.txt` required.

## R13 — What the adversary pass (iteration 29) read in Stryker 10.0.0's own source (T036–T044)

- **Reuse (T036).** `core/dist/src/mutants/incremental-differ.js` reuses an earlier result for `!mutant.status && !options.force`;
  `--force` ("Run all mutants, even if --incremental is provided and an incremental file exists") is the one switch that
  closes every route, whatever `incremental` and `incrementalFile` say, so the wrapper passes it on every run and also
  removes the default file and the config's `incrementalFile` where that stays inside the service.
- **Which comment ignored a mutant (T039).** `instrumenter/dist/src/transformers/directive-bookkeeper.js` attaches a
  directive to the node whose `leadingComments` it is (so blank and comment-only lines between a comment and its code do not
  separate them), matches a `next-line` rule on that node's start line, and chains rules from the latest: the first rule that
  names the mutator (or `all`) answers, a `restore` included. The `statusReason` is that rule's reason, or `Ignored using a
  comment` where it gave none, so a block `disable` and a `next-line` one differ in the report only by that reason. Lines are
  Babel's: `\r\n`, `\n`, `\r`, U+2028, U+2029, never a form feed.
- **Planted nothing (T037).** Probed with the instrumenter over one file each, `plugins: null`, `excludedMutations: []`: the
  ambient forms (`declare const|let|var|function|class|namespace|module|global`, `export {}`), enums with and without
  initialisers, and type unions gave 0 mutants. The reader still treats an initialiser as code, which fails closed.
- **The closure (T044).** `@stryker-mutator/instrumenter` resolves `@babel/*` and `weapon-regex` through ranges; the wrapper's
  `versions` follows `dependencies` and `optionalDependencies` as npm resolves them (the package's own `node_modules`, then
  each parent's) and keys every entry by its lock path.
